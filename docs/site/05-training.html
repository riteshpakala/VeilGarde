How is each shipped model trained?

On the training regime: every model the detector trains, trained from stored features in Swift, and measured on rows it did not see.

The detector trains three kinds of model: the camera head, the linear heads and the combiner that pools them. VeilGarde trains each in Swift, from the features-only store, and writes a bundle the detector runs as it is.

The backbones are the exception. DINOv2 is imported from its published checkpoint, never trained here, and its bytes are pinned.

A run is one declaration

A training run is one recipe, written the way the detector's pipeline is: one trainable member per line, with an if or a for where the set depends on something. Each member is a value with copy modifiers, so nothing is built until the engine runs it.

The detector is declared the same way, its stack's members and its revisions in order:

The two declarations match on purpose. A new specialist is one file and one line on each side: a member that scores the image in the pipeline, and a trainable member that fits it in the recipe.

The shipped recipe grows the camera head from scratch, trains the art, blur, human and preview heads, and fits the combiner over them. The screenshot and semtile heads are not in it: the store keeps no screenshot rows and no patch tokens to train them on.

The engine has two calls, and knows no member by name. The plan asks each member what it would do: its stages, whether each runs and why, and any refusal, reading files and touching no GPU. Training plans first, so a refusal stops the run before a candidate exists, then asks each member to train itself.

A candidate starts as a copy of its parent bundle. Each trained model replaces its parent's file, every write re-hashes the manifest, and the whole candidate is verified at the end. veilgarde route --bundle runs it.

The camera head is a tree ensemble

The camera head is a gradient-boosted ensemble, and there is no XGBoost in Swift. VeilGarde's trainer reproduces XGBoost 3.2's histogram method decision for decision. Gradients and gains are single precision and histograms double, each sibling's histogram is built by subtraction, and ties break toward the lower feature, then the lower bin.

On integer features its trees equal XGBoost's node for node, in three configurations. On continuous features the bins differ slightly, and the AUC stays within 0.005. A warm start copies the parent's trees into the new file verbatim, so they stay byte-identical.

The camera head

The shipped head was grown from scratch on the day the warp left detection. The head before it also read the warp score and sharpness, and a warm start cannot continue a head on columns its parent never read. The trainer refuses that, and the plan says so before anything trains.

Each row is the store's DINOv2 embedding and its nine capture values, in the head's own order. Rows from the newest generators carry their own weight, and 30% of them stay out of training, so the recall reported on them is held out.

A head trained on every row has no held-out AUC of its own. So the trainer first fits a twin the same way without a tenth of the rows, chosen by a hash of the row's id, and scores the twin on them. The written head still trains on every training row; the twin is measurement only.

The heads

Each head is a standardized logistic regression, fitted by Newton's method to sklearn's own objective. It reaches sklearn's optimum within 1e-5. Each kind keeps its shipped recipe: which rows are positive, which negative, the regularization, the class weights, and a test split by source.

The combiner

The combiner pools the camera head, its anchor, with the art, blur and human heads on images with no capture signature. It is fitted with every weight held at zero or above, so no evidence can be counted backwards. Each real row counts three times, so a false alarm on a real photograph costs more.

It writes the combiner keyed by member: the anchor's weight, each evidence member by name with its weight, and the rescue.

Its rescue weight is chosen by a sweep that must keep every protect-real probe real and none above 0.42. On this refit every candidate weight kept the probes real, but the highest stayed at 0.4645, so the sweep chose none and the combiner took the fallback.

The backbones

DINOv2 is not trained here; it is imported. The import starts from Hugging Face's checkpoint, renames each tensor, moves the patch convolution's axes, and resizes the 37×37 position grid to 16×16 for a 224-pixel input.

That resize has to be PyTorch's, bit for bit, or the file would differ from the shipped export. Plain single-precision arithmetic matched 44% of the values. Fusing the multiply-adds the compiler fused in PyTorch's kernel, in the source position, the weights and the sums, matches every value at every scale tried.

The imported small file is byte-identical to the shipped one, so its hash is the manifest's pin. The F16 and 8-bit variants match the reference export tensor for tensor.

For engineers: where each piece lives
  • Training's folders run in order: Data, Extract, Boost and Linear, then Camera, Heads and Combiner, then Recipe with its Members, Engine and Artifacts, and Backbone for the imports.
  • A trainable member conforms to TrainableMember: its name, its rank, its plan and its training. CameraHead, SpecialistHead and Combiner are the three; TrainingRecipe.kinds lists the types a recipe file may name.
  • veilgarde train plan --preset prints the shipped recipe's plan without training; train all trains it; train camera, train heads and train combiner train one member; train run <recipe.toml> trains a recipe file with [camera], [heads] and [combiner] tables.
  • Train in release: VEILGARDE_CONFIG=release scripts/cli.sh train …. The store defaults to the work area's store/shards.
  • The tests hold the trainers to references written once in Python: XGBoost's trees, scikit-learn's logistic fits and scipy's bounded optimum.
