# VeilGarde's site

The site is VeilGarde's docs and its change explorer in one folder of plain HTML. It shows every file the run changed, verbatim, before and after; each Swift declaration with what it calls and what calls it; eleven trails, which tell each flow in the order the code runs; the run's ledger; and the chapters that explain each layer. Double-click `scripts/site.command`, or open `docs/site/index.html`. Nothing to install, no server, no network, except the ask orb's one call when a reader sends it a message.

| Page | What it is |
|---|---|
| `index.html` | the change at a glance: the request, the trail grid and the layers lit by each step, the counts, the ledger's commands, tests and decisions, open questions, what was left out |
| `code.html` | the explorer: the tree, the source with old, new and diff, the declaration's card, the trails, find |
| `selfcheck.html` | every check the browser can make, run when the page opens |
| `01-warp.html` … `09-playground.html` | the chapters, one per layer: the warp lens, the bundle, the fusion base, the specialists, the router, training, the flywheel, the watermark, the playground |

## Rebuilding and checking

```
docs/site/src/build.sh                              # build.py --self-test, build.py, then check.py
python3 -I docs/site/src/build.py                   # data/run.js, data/index.js, data/files/<group>.js
python3 -I docs/site/src/build.py --self-test       # the Swift parser, the hunks and the key scan against hard shapes
python3 -I docs/site/src/build.py --stats           # unresolved and likely call names, id collisions, what was left out
python3 -I docs/site/src/build.py --dump Sources/VeilGardeLens/Warp/WarpLens.swift
python3 -I docs/site/src/check.py                   # every page in Chrome, lint, data freshness, the key scan
python3 -I docs/site/src/check.py --prose           # the prose rules, every warning listed
python3 -I docs/site/src/askkey.py                  # the orb's key into local/ask.js; scripts/site.command runs it
```

`build.py` is Python's standard library only. It is deterministic: a second run on the same tree writes no file, and it never writes a file whose bytes would not change. `check.py` needs Playwright and Google Chrome. Neither runs Swift, MLX or the GPU.

Run `build.sh` after any change to the code, the ledger, the trails or the site itself. `check.py` fails when a file changed after the build, when the change set gained or lost a file, or when `ledger.json` or `trails.json` moved, and says to rebuild.

## The constraints a page lives under

The site is read from `file://`. Chrome blocks `fetch()` of a local file and `<script type="module">` imports there, so:

- data ships as classic scripts that assign into one global, `window.VeilGardeData`; each data file starts with `/* generated by docs/site/src/build.py - do not edit */` and then `window.VeilGardeData = window.VeilGardeData || {};`;
- page code is classic scripts on one other global, `window.VeilGarde`, each wrapped in one function; there are exactly two globals, and `check.py` compares every page's window with a fresh one;
- a page loads `data/files/<group>.js` by injecting script tags: `body[data-groups]` names the groups, `all` for the explorer, and every `data-excerpt` adds its own; a new target group needs no HTML edit;
- every URL is relative; `fetch` appears once, in `js/ask.js`, to `https://api.mistral.ai/v1/chat/completions`;
- `localStorage` can throw, so every read and write is wrapped and the pages work without it;
- light and dark follow `prefers-color-scheme`; every page works at 390 px with no sideways scroll, and every control is reachable by keyboard.

## The change set

From an empty repository, git's empty tree, to the working tree: `git diff --name-status -M <empty tree>` plus the untracked files git does not ignore. Each file keeps its status, its base text from `git show`, its text from disk, and git's hunks, checked by applying them. Left out, and listed by name and size on the overview: everything under `Sources/VeilGardeInference/Resources/`, every `Tests/**/Fixtures/**` file, `*.safetensors`, `Package.resolved`, `LICENSE`, anything gitignored, binaries, secret-shaped file names, and any file holding a key-shaped string, whose kind and line are printed but never the string. The site's own `data/` is the build's output and not part of the change.

The data's cap is 3 MB; the build prints the size. Over the cap it drops the base text of the least-changed modified files, then the edge counts, and never a changed file.

## Declarations, ids and calls

Every Swift file is lexed, strings, raw strings, interpolation and comments included, and its braces walked, a port of Braid's `docs/site/src/sources.py`. Its declarations are counted twice, by the walk and by a plain keyword count with strings and comments blanked, and the build fails on any file where the two differ. A declaration's id is `<path>:<Qualified.name>(<labels>)`, with `extension:<Type>` for an extension and `~2`, `~3` only for true duplicates. The pages derive the same ids, and the self-check compares the two on a sample.

Calls are matched by name and argument labels when the page is built, not by a compiler, and every edge says how: **exact** when the type is named or implied and one declaration fits, **likely** when the name and labels are unique but the receiver's type was not read, **ambiguous** when two to eight fit, all listed. Names that are also Swift, Foundation or MLX methods keep only exact edges. Edges are `[from, to, tier, line, count]`, with the tier an index into `["exact", "likely", "ambiguous"]`.

Python, shell, Markdown, JSON, HTML, JavaScript and CSS files are shown with their hunks and their header, without declarations.

## Deep links

`code.html` reads `#<path>` for a file, `#<path>:<line>` for the declaration at that line, `#<path>:<id tail>` for a declaration by id, `#trail-<trail>-<n>` and `#trail-<trail>-<n>;n=<k>` for a step of a trail, and `#q=<text>` for a search, and writes the current place back with `history.replaceState`. A link of the one trail's old form, `#trail-<n>`, still lands where that step lives now, and so does a step of a renamed trail: `V.trailRenamed` in `js/veilgarde.js` maps the watermark's one trail onto its signing and matching trails. `index.html#step-<trail>-<n>` lights a step; `index.html#decision-<n>`, `#command-<n>` and `#test-<n>` open a ledger row.

## The trails

`src/trails.json` holds the trails, each `{id, kind, title, mark, subtitle, say, steps}`. The kind is `training`, `inference`, `signing`, `matching` or `research`: the column the trail sits in and the colour of its mark and badges; the id is lowercase words joined by hyphens and the mark is short and its own. A trail holds 3 to 9 steps, each `{n, title, chapters, entries}`, where `chapters` names the pages a reader follows the step in, and each entry is `{scope, anchor, note, cite}`, with `status` and `"link": "none"` optional. The build fails when:

- `scope` does not resolve to exactly one declaration; write `Type.method(labels:)`, or put `File.swift:` in front when the name is shared;
- `anchor`, a fragment of the code, is no longer inside that declaration, so a later edit fails the build instead of pointing at the wrong line;
- `status` differs from what the build computes: `added`, `changed` or `unchanged`;
- the note uses a banned phrase or a parenthesis, or the cite does not resolve;
- a declaration takes two places on one trail, or a step names a chapter that is not a page.

A cite is one of: `ledger#<id>`; `PIN` or `WHAT`, the entry's own file's header, or `PIN:<path>` for another file's; `test:<the @Test display name or test function>`; `doc:<declaration>`, its `///` comment; `comment:<path>#<words inside a comment>`; `<file>.md#<heading>`. With no cite, the note says only what the code does.

A note is one or two plain sentences: what the declaration does, then why it is built this way. The build warns when an entry has no call to or from the entry before it and is not called by an earlier entry, unless it says `"link": "none"` because the hand-off is through data. A declaration takes one place on a trail and may sit on several trails, anchored differently on each.

There are eleven trails. Training: the warp model (WT), the fusion head (FT), the specialist heads and the combiner (ST), the noiseprint (NT). Inference: the warp lens to the camera-sensor score (WI), the router to the fusion base (FI), the specialists to the final verdict (SI), the noiseprint's camera evidence (NI). The watermark: signing, an image to its signature (WS), and matching, a crop or a re-encode to its place and score, the acceptance run last (WM). Research: the pruning study (PS). To change one, edit `src/trails.json` where the code runs, keep `n` from 1, and rebuild. The overview's grid and stepper, the picture's lit layers and the explorer's grid, steps, badges and card follow the data.

`src/trails.json`'s `picker` lays the trails out as one grid, read the same on the overview and in the explorer: sections of rows, each section `{title, kinds, rows}`, each row `{label, trails}` with one trail for each of the section's kinds, in their order. A row is a flow and a column a kind, so a flow's training and its inference sit side by side, and every cell is as wide as the cells above it. A section with fewer kinds than the widest spans its last column. The build fails when the picker misses a trail, holds one twice, or puts one in another kind's column. The arrow keys move between cells.

## The chapters

A chapter is `NN-<slug>.html`, listed in `VeilGarde.pages` in `js/veilgarde.js`, which drives the side list and previous and next. Its shape:

```html
<body data-groups="Sources-VeilGardeCore,Sources-VeilGardeLens">
  <a class="skip" href="#main">Skip to the chapter</a>
  <div class="shell"><nav class="side" aria-label="Chapters"></nav>
  <main class="page" id="main">
    <header class="top">…menu, chapter N of 9, a link…</header>
    <h1 id="ch-<slug>">The question</h1>
    <p class="lede"><em>On what the chapter is about, in one line.</em></p>
    <p>Prose…</p>
    <div class="code" data-excerpt="<declaration id>"></div>
    <span data-fact="calibration.decision_threshold" data-round="5">0.62987</span>
    <h2 id="sources">Where the numbers come from</h2> … a table: number, source, when …
  </main></div>
  <script src="js/veilgarde.js"></script><script src="data/index.js"></script>
  <script src="js/chapters.js"></script><script src="js/ask.js"></script>
  <script>VeilGarde.mount();</script>
</body>
```

- `data-excerpt` quotes a declaration by its id from the same verbatim data the explorer holds; a renamed declaration fails the self-check.
- `data-fact` names a path into `index.facts`, which the build reads from the shipped manifest and calibration; `data-round` or `data-prefix` says how it is written; the self-check compares the page's number with the data.
- `js/chapters.js` holds a chapter's live tables and its checks against the code, such as the feature table against `WarpFeatures.names` and the result keys against `ResultJSON.swift`.
- To write a placeholder chapter, replace its `later-block` with prose, add `data-groups` for any excerpt's file, add `chapters.js` if it uses a live table, and drop `later: true` from its entry in `VeilGarde.pages`.

The voice: say the idea first in one plain sentence, then earn it; short sentences; one idea per paragraph. No hedging, no salesmanship, no "simply" or "just", no parenthesis inside a paragraph. Every number names its source and date; a number VeilGarde did not measure is marked as quoted; a reason that was not recorded is written "not recorded". `check.py --prose` fails on the banned phrases and on a parenthesis in a paragraph, and lists long sentences and number-heavy paragraphs.

## The ask orb

Every page has an orb at the bottom right, half seen until a pointer or focus finds it. It opens into a mini chat about what the reader is looking at; × or Esc folds it back, and "New chat" forgets the conversation and stops an answer in progress.

- **What it reads.** On `code.html`, the selected declaration: its code with the editor's line numbers, capped at 220 lines; its doc comment and its file's WHAT and PIN; its change; its trail step, note and cite; its calls and callers with their tiers. On any other page, the page's visible text, capped at 9,000 characters. The panel's header names what it reads and follows the selection.
- **The rest of the change, on the explorer.** Every request there also carries a map: every file with the first sentence of its header, folder by folder, then the trail's steps, the sentences cut shorter until the map fits about 24,000 characters, some 6,000 tokens. The model gets four tools the page runs from the data it already holds, so a read costs no extra call: `find_declarations`, `read_declaration`, `search_text` and `read_file`, each capped at 14,000 characters. A question gets up to five rounds of reading; the last sets `tool_choice: "none"`. Words from a round that only reads are dropped, and the answer lists what was read, each a link to that place.
- **The call.** `POST https://api.mistral.ai/v1/chat/completions` from the browser, `stream: true`, `mistral-large-4` with `reasoning_effort: "none"`, one system message and the last 12 turns. Replies are built from text nodes, never as HTML; a `File.swift:line` in a reply links to that line. Errors say in plain words that the key was refused, is rate-limited, or that there is no network. `VeilGarde.ask.transport` can be replaced.
- **The key.** `src/askkey.py` reads `MISTRAL_API_KEY` from the environment, else the `MISTRAL_API_KEY` entry of a local key store, `~/.rao/keys/providers.json`, and writes `local/ask.js` with mode 600, after git confirms it ignores that path; `.gitignore` holds `/docs/site/local/` in both spellings. It never prints the key. The page loads `local/ask.js` only when the orb first opens. Without it, on another engineer's copy of the site, a dialog opens with the chat and asks for the reader's own Mistral key; the key stays in that browser's storage and goes only to Mistral's API, "Forget the key" is beside the chat, and a key Mistral refuses is forgotten and asked for again. `?ask-key=none` on any page shows the site as that engineer sees it, skipping `local/ask.js`.
- **The checks never call Mistral.** Every Chrome run refuses every network request, `api.mistral.ai` included, and fails if a page tries one. The orb's test swaps the transport for a stand-in: half seen, whole under the pointer, open with focus in the box, a question whose system message names the selection, and on the explorer carries the map and the four tools; the stand-in asks to read `WarpInference.run`, and the test checks the second request carries the read and the answer lists it; New chat empties the log; Esc returns focus to the orb. A second test opens `index.html?ask-key=none` and walks the dialog: it opens modal with the field focused and the chat locked, Not now leaves a way back, an empty key is refused in place, a key unlocks the chat, a refused key is forgotten and asked for again, and Forget the key asks again. `check.py` also scans every file git can see for the key's value and prints only the number of hits.
